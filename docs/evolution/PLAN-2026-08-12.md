## 2. The 4 streams — detailed

### 2.1 Research (general agent, background)

**Goal:** ensure the v0.2 PEP's external claims (Neuraxon, Qubic, OC, BPP-9000,
Oracle Machines) are still accurate on 2026-08-12. Surface any drift.

**Tasks:**
1. Re-fetch the Qubic All-Hands Recap (most recent) and confirm the
   BPP-9000 / OC / OM status claims in `Appendix A` of v0.2.
2. Re-check the Neuraxon 2.0 GitHub repo for new commits / releases since
   2026-05-28 (the date in v0.2). Report any new `cuNxon` versions.
3. Verify Neuraxon 2.0's ARC-AGI-3 score (was 0.21% on 2026-07-22). Has it
   moved?
4. Verify Neuraxon 2.0's AGI-26 paper status (was accepted). Has it been
   presented yet? Any revisions?
5. Check for any new Qubic blog posts on OC mainnet, BPP-9000 performance,
   or OM traffic numbers.

**Deliverable:** `docs/evolution/RESEARCH-AUDIT-2026-08-12.md`
- A table of the v0.2 claims, each marked ✅/⚠️/❌ vs. the 2026-08-12
  source. Include direct quotes / screenshots where the claim changed.
- A "drift log" section listing any 2026-08-12 news that would change a
  v0.2 decision.

**Verification:** the verifier opens at least one link per claim category
and quotes the page. Cites must include date.

### 2.2 Design (general agent, background)

**Goal:** produce the three ADRs that the build stream will implement
against. These are the *contracts*.

**Tasks:**
1. **ADR 005 — Organism Primitive.**
   - Use `docs/architecture-decisions/003-trinary-protocol-v1.md` as a
     template.
   - State the decision: "Adopt the Organism primitive in `services/ann`
     (additive), as specified in v0.2 §6."
   - List the consequences — both positive and negative. The negative
     list must include at least: "The Organism primitive requires every
     consumer of the ANN primitive to understand the additional state
     machine (genome, environment, objective, fitness, lineage, memory).
     A consumer that treats an Organism as just an ANN with extra fields
     will misread the lifecycle."
   - State the alternatives considered: (a) separate `services/organism`
     service — rejected because it duplicates auth/audit; (b) extending
     `services/tissue` instead of `services/ann` — rejected because the
     tissue contract is stateless per call.

2. **ADR 006 — Work Runtime.**
   - State the decision: "Adopt the Work Runtime in a new
     `services/work` (port 7012), as specified in v0.2 §11-§15."
   - List the negative consequences: "Adds an 11th service to the
     monorepo. Increases operational surface. Verification in v1 is
     replication + challenge + reputation, NOT ZK — the platform does
     not yet have evidence that this is insufficient."
   - Alternatives: (a) extend `services/compute` — rejected because
     `services/compute` is the Aigarth Core reservation engine, not a
     general work scheduler; (b) extend `services/training` — rejected
     because training is a specific recipe type, not a general work
     abstraction.

3. **ADR 007 — OC Processor.**
   - State the decision: "Aigarth registers as a Qubic OC *processor* in
     Phase 29. The trust root is the 451/676 computor signature."
   - List the negative consequences: "Aigarth is exposed to
     compute-on-demand from any Qubic smart contract. Rate limits +
     circuit breaker (existing M4 pattern in `services/qubic`) are
     mandatory before mainnet exposure."
   - Alternatives: (a) Aigarth as an OC *client* (Aigarth calls Qubic
     for compute) — rejected because OC is outbound, not inbound; (b)
     custom Qubic protocol changes for useful work — deferred to Phase
     30+ research.

**Deliverable:** `docs/architecture-decisions/005-organism-primitive.md`,
`006-work-runtime.md`, `007-oc-processor.md` (3 files).

**Verification:** each ADR is opened and grep'd for `## Decision`,
`## Consequences`, `## Alternatives`. The verifier checks that the
`## Consequences` section contains at least one *negative* bullet
(grep `^- ` lines containing words like "risk", "downside", "cost",
"exposure", "operational"). If the negative is missing, FAIL.

## 4. Coordination protocol

The four Wave 1 agents run in parallel (background tasks). The orchestrator
monitors them with `task_query` / `task_output`. The verifier runs *after*
each stream's deliverable lands, not concurrently (the verifier is the
gate; it needs the input).

If any Wave 1 agent reports FAIL from its own self-check, the orchestrator
re-spawns it with the specific failure named. Two consecutive FAILs on
the same task = stop and ask the user.

If any Wave 1 agent produces output that the verifier flags as a real
defect (not a stylistic nit), the orchestrator opens a `FIX-<n>.md` note
in `docs/evolution/` and re-spawns the producer with the fix named.

## 5. The two hard rules

1. **No `pnpm dev` / `pnpm stack:dev` from the orchestrator.** Background
   agents that need the stack should start it themselves in their own
   subshell. The orchestrator's stack is the verification stack.
2. **No edits to v0.1** (`aigarth-cloud-evolution-pep.md`). v0.1 is
   frozen as the historical record. v0.2 is the live doc.
