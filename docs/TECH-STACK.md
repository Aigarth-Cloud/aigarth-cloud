## 1. Stack philosophy

Default to boring, well-supported tools. Every choice must answer: **why this over the obvious alternative?** If we can't articulate the why in one sentence, we don't use it.

Local-first. Every tool must run on a developer's laptop without external services. Cloud-managed equivalents can be wired later, but the dev experience must not require them.

## 2. Languages

| Layer | Language | Why |
|---|---|---|
| Front-end | TypeScript (strict) | Shared types with the SDK; large talent pool |
| API services | TypeScript (Node 20+) | Same runtime as front-end; shared types |
| API services (long-running) | Go | Performance, single binary deploy, ops-friendly |
| SDKs | TypeScript, Python, Go, Rust, Java, C# | User demand — OpenAI has 6 SDKs, so do we |
| CLI | TypeScript (Node) | Ship with the SDK; share code |
| Worker jobs | TypeScript initially, Go for compute-heavy | Easy to start, fast when needed |
| Smart contracts | C++ (Qubic style) | The Qubic network requires it |

## 3. Frameworks

| Concern | Choice | Why |
|---|---|---|
| Web framework | Next.js 14 App Router | Existing codebase; great DX; static + dynamic |
| API framework | Fastify (Node) or stdlib http (Go) | Fast, low overhead, good observability |
| Background jobs | BullMQ (Node) / River (Go) | Queue + cron + retry in one |
| API gateway | Kong or self-hosted (Traefik + auth) | Centralized auth, rate limiting, request shaping |
| API docs | OpenAPI 3.1 + Redoc | Industry standard, autogenerated clients |
| Auth | Auth.js (NextAuth) for the app, custom for the API | Standard for the front, controlled for the API |

## 4. Data

| Concern | Choice | Why |
|---|---|---|
| OLTP | PostgreSQL 16 | JSONB for flexible sub-objects, mature tooling |
| ORM | Drizzle (TypeScript) | Type-safe, lightweight, SQL-first |
| Cache | Redis 7 | Sessions, rate limits, leaderboards |
| Search | Meilisearch | Easy to operate, fast enough for v1 |
| Analytics | ClickHouse | Cheapest path to billion-row event tables |
| Object storage | S3-compatible (R2 in prod, MinIO locally) | Models, artifacts, logs |
| Queue | NATS JetStream | Fast, supports queue + pub/sub + KV in one binary |

| Concern | Choice | Local | Production |
|---|---|---|---|
| Containers | Docker + Compose | yes | yes |
| Orchestration | Fly.io Machines or AWS ECS Fargate | — | yes |
| Postgres | Docker (local) → Neon or Supabase | yes | managed |
| Redis | Docker (local) → Upstash | yes | managed |

| CDN | none (local) → Cloudflare | — | yes |

## 6. Dev tools

| Concern | Choice | Why |
|---|---|---|
| Package manager | pnpm | Fast, strict, monorepo-friendly |
| Monorepo | TurboRepo (initial) | Caching, task graph, simple config |
| Testing | Vitest (unit), Playwright (e2e) | Fast, good DX, both TS-native |
| Lint + format | ESLint + Prettier | Standard |
| Type check | TypeScript strict | Required |
| Pre-commit | Husky + lint-staged | Block bad commits |
| CI | GitHub Actions | Standard, generous free tier |
| Secrets (dev) | `.env` files | Simple |
| Secrets (prod) | Doppler or AWS Secrets Manager | Rotation, audit |

## 7. Front-end specifics

| Concern | Choice | Why |
|---|---|---|
| Styling | TailwindCSS + shadcn/ui | Existing codebase, fast iteration |
| Animation | Framer Motion | Declarative, performant |
| Icons | Lucide | Tree-shakable, consistent |
| Forms | React Hook Form + Zod | Performant, type-safe validation |
| Client state | Zustand | Lightweight, no boilerplate |
| Server state | TanStack Query | Caching, retries, optimistic updates |
| Auth (UI) | Auth.js | Standard, social providers |
| Charts | Recharts or Visx | Recharts is simpler, Visx is more flexible |
| Tables | TanStack Table | Headless, composable |
| Markdown | MDX | Docs as code |

## 8. Why not X (alternatives we considered)

| Considered | Decision |
|---|---|
| Remix | Next.js has better ecosystem and we already have a Next.js app |
| tRPC | Great, but not all our SDKs are TS. OpenAPI-first is more portable |
| GraphQL | Powerful but the back-end complexity isn't worth it. REST + OpenAPI is enough |
| Prisma | Good but heavy. Drizzle is SQL-first, type-safe, and lighter |
| AWS-only | Lock-in. Multi-cloud matters for the enterprise story |
| Vercel-only | Same lock-in risk. Fly.io + Cloudflare is a healthier combo |
| SvelteKit | Smaller community, fewer devs. Next.js wins for hiring |
| Rust for everything | Great for compute, overkill for API services. Node + Go is enough |

## 9. Decision log

Decisions captured here are the ones that future maintainers will ask "why?". If a choice is obvious, it doesn't go here.

| Date | Decision | Rationale |
|---|---|---|
| 2026-07-27 | pnpm over npm/yarn | Speed, strict mode, monorepo support |
| 2026-07-27 | Drizzle over Prisma | SQL-first, lighter, better for services |
| 2026-07-27 | NATS over Kafka | One binary, simpler ops, supports our workload |
| 2026-07-27 | Next.js 14 App Router | Existing app, good DX, static + dynamic |
| 2026-07-27 | SQLite (local) → Postgres (prod) | Local-first; can swap when service lands |
| 2026-07-27 | OpenAPI over GraphQL for public APIs | Portable, autogenerated clients, simpler |
